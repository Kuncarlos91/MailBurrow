# MailBurrow Playbook

[Main documentation index](../README.md) · [Setup guide](setup-guide.md) · [Troubleshooting](troubleshooting/README.md) · [Maintenance rules](development/documentation.md)

How MailBurrow works today: features, safety rules, architecture, the Mail-Archiver API it uses and the design decisions behind it. Update it in the same change as the code it describes.

## Purpose and scope

MailBurrow is an independent, read-only Flutter client for a Mail-Archiver server. Shared Dart UI supports Android and iOS/iPadOS, with native credential storage, attachment save/open handling and signing. It does not connect directly to Gmail or change archived messages. The operator manages sync, users, API-key permissions and retention.

This describes the current source. Update it with implementation changes; release history is in the [changelog](../CHANGELOG.md).

Folder decoding is bounded independently of the API byte limit: at most 2,000 folders and depth 32 (root zero), with iterative Mail-Archiver traversal, validated names/paths (at most 8,192 characters each), non-negative counts and unique paths. Bichon mailbox lists share the count/depth limits. The folder picker creates visible rows lazily; an excessive or malformed response fails without publishing a partial list.

Setup's general introduction and server selector use `ArchiveServerType.values` as the backend-name source. A widget regression checks that every offered type appears in the introduction, including future entries. This wording fix is unreleased; the published 0.5.0 screenshot accurately retains the earlier sentence.

## Navigation and connection

Setup shows the same stamped app version/build information as Settings, without requiring a server connection. An unstamped development build says “Build information not supplied” rather than guessing a release identity. This setup footer is a development change and does not alter the published 0.5.0 APK.

Mail, Search and Settings share one configured server/key. All three show the same current-archive and account rows at the top (`CurrentArchiveRows` in [current_archive_rows.dart](../lib/widgets/current_archive_rows.dart)); the archive row opens the archive picker and switches through the same `switchArchive` path from any tab. The Switch account app-bar button, the account row and the account rows in Settings' archive information open an account picker. It fetches the accounts endpoint with the configured key and offers only returned entries.

Selecting another account cancels/invalidates old mail/folder work, saves its numeric ID in the existing encrypted connection JSON, clears previous messages/folders/query/filters/page/errors and returns to Mail at page 1. The new account's messages/folders then load independently; failures show no previous-account data. Messages remain in their original server accounts; there is no local cross-account mail cache, moving, merging or deletion. Each list/folder request uses the selected account ID, and late old results are ignored. This is shared Android/iOS/iPadOS behavior. A storage failure leaves the previous account selected and reports a sanitized error. The picker remains usable during pending mail loading and is scrollable at large text sizes. A pinned, accessible Switching account progress indicator remains visible while secure selection and the new mail/folder loads are in progress, even when the list was scrolled down. Generation guards prevent an older switch completion from clearing a newer switch indicator. Selecting the current account or cancelling does not reload mail.

On startup, older connection records without accountId select the first returned account and are migrated on successful connection. A remembered ID is restored only if the current accounts response includes it; otherwise the first accessible account is used with a notice and the stored ID is updated. No credentials or mailbox permissions change, and no separate account list/messages are persisted. Server authorization remains authoritative.

Hostnames without a scheme normalize to HTTPS. Explicit HTTP, embedded credentials, query/fragment-bearing addresses and invalid ports are rejected. Optional base paths are preserved. Certificate validation stays enabled, redirects are disabled, and credentials go only to the configured archive. Tailscale is user/operator infrastructure: no network settings or sharing configuration is bundled.

**Demo mode.** **Try the demo** on setup opens a built-in archive of fictional mail instead of a server. `ArchiveSession.startDemo()` adopts a `DemoArchive` without address validation, network access or secure storage, so entering, browsing and switching demo accounts never read, write or delete the saved connection. Exiting with no return archive also uses no storage. When exit reopens a prior real archive, the normal switch path reads its credentials and may update the active profile/account selection; it does not add a new archive. Restore on launch never opens the demo, because it is never stored. A **Demo · sample mail** banner with **Exit** is shown on every screen while the demo is open, including Connection settings opened from it and the message reader. `exitDemo()` (the banner, **Settings → Exit demo**, or Disconnect while in the demo) closes the demo backend, which stops attachment copies in progress and deletes partial files, invalidates in-flight requests, then reopens the saved archive that was open when the demo started (with the **Opening <label>…** screen and Cancel), or returns to setup if the demo was started with nothing open or that archive was forgotten meanwhile. Reopening contacts that archive's server, exactly as switching to it does; a previously saved real connection can still be retried from setup. Connecting to a real server from setup replaces the demo. The banner's text scaling is capped at 2x so it stays a compact bar at the largest text sizes.

Connection details use platform secure storage (see [connection_store.dart](../lib/state/connection_store.dart)). Default-trust indexes retain version 3. Indexes containing custom-trust markers use version 4 so older builds reject the entire index before connecting or rewriting it. Removing all custom-trust markers permits v3 again. The store keeps:
- **an index** under `connections`: the version, the active profile ID, and per profile an opaque random ID, a label (the host by default, at most 60 characters), the **server type** (`mail-archiver` or `open-archiver`), the server address and the selected account ID **as text**. The index holds no keys.
- **one key entry per profile** under `connection.key.<id>`.
- for an archive with its own certificate, `"ownCertificate": true` in its index entry (omitted otherwise) and **one certificate entry** under `connection.trust.<id>`: version 1, the server type and address it was trusted for, the DER bytes (base64) and their SHA-256. A read uses it only when the type and address still match and the fingerprint checks out; stored text/base64 are capped before JSON/base64 allocation; a missing, damaged, mismatched or newer-version record throws `SavedCertificateUnavailable` and is left as it is, never downgraded to default trust. An index entry with any other `ownCertificate` value is kept aside as unreadable. Older v3 builds refuse a v4 index, rather than ignoring or erasing the trust marker; a v3 index claiming custom trust is refused by this build too.

Writes are staged so one failure never breaks another profile or the working key:
- a changed type, address or key is written under a fresh ID before the index points to it, and the old key entry is deleted only afterwards;
- an account-only change rewrites just the index;
- a certificate moves with the key under the fresh ID only when the server type and address are unchanged; a changed type or address starts from default trust, and a damaged record that should move stops the write. Replacing or removing the certificate (`ConnectionStore.setCertificate`) is staged the same way and keeps the active selection. Forget, Disconnect and forget, and the all-archives reset remove certificate entries with the keys; unreferenced certificate entries are removed on read, while those of unreadable profiles are kept. Certificate bytes are snapshotted before a change waits in the queue; cleanup after a failed stage is best effort and retried on a later read. The stored hash detects an inconsistent record, not malicious access to secure storage. The session passes each archive's certificate to its connections: restore and switching use the saved one; setup uses a certificate confirmed with `setPendingCertificate` only for the exact server type and address entered at that moment, and saves it with the archive (it is cleared with the unsaved key, and dropped if the destination changed); **Change address or key** keeps the archive's certificate only when the type and address are unchanged, and checks the new key with it. A `SavedCertificateUnavailable` record stops restore, switching and reconfiguring with a message, and nothing connects without it. `setArchiveCertificate` stages a replacement or removal and, for the open archive, reopens it so no old connection is reused. `certificateNotVerified` is only a TLS-failure hint for setup to offer the certificate flow: it doesn't prove an unknown CA, nor that earlier requests in a multi-request attempt sent no credential, so UI copy stays generic. A confirmed pending certificate is size-checked, bound to the canonical destination and cleared on invalid input. A certificate change blocks session navigation until it's saved; the affected connection is closed before the storage write and reopened only after it commits, and a failed save leaves it closed for an explicit Retry with the previous record intact. Retry and reconfigure references follow the staged profile ID. Test-only single-type `apiFactory` sessions ignore certificates;
- key entries the index does not reference are removed when it is read. Reads, migration, saves, forgetting and cleanup share one transaction queue across store instances in the app isolate; other isolates must route storage operations through that owner. Cleanup after an index commit is best-effort and retried on later reads.

Settings → Archives is a single-choice radio list: the open archive's radio is selected and its row tinted, and tapping another row switches to it through the same `switchArchive` path as the Mail page's archive row (old browsing state cleared first, progress and Cancel/Retry shown by the home screen). Other rows are disabled whenever switching is not allowed. Each row's ⋮ menu is a separate accessible action beside the radio selector; it renames, changes ("Change address or token" for Bichon) or forgets.

Profiles this build cannot read are kept as stored, with their keys, and count toward the 20-profile limit. All records sharing a duplicated ID are unreadable; restoration never picks the first. An unknown-version or malformed index is preserved, and ordinary save/forget operations refuse to overwrite it; recovery requires a build that understands it or the explicit all-archives reset: setup offers **Remove all saved archives…** only when the index cannot be read, explains that every saved archive and key on this device will be removed and that server mail is unchanged, and acts only after confirmation (`ConnectionStore.reset`, which never contacts a server and removes nothing if the stored entries cannot be listed). Reset removes credentials first and the index last; a deletion error reports failure and leaves recovery available for retry. An unreadable legacy record also offers the confirmed reset. Adding another archive first migrates any readable legacy connection, preserving it as a separate profile. Older builds kept one record under `connection`: version 2 (server type, address, key, account text), or version 1 from 0.3.0-rc.9 and earlier (no version or server type, numeric account ID), read as Mail-Archiver, the only type those builds supported. A readable legacy record migrates to one profile and is deleted only after the new entries are written. An unreadable one is left untouched for recovery. If both exist, the index wins and the legacy record is removed. An explicit null version, a server type without a version, an unknown version or server type, or an active profile without a key makes the saved connection unreadable, so restoration reports an error. Per-profile errors leave other records intact; whole-index errors block mutation. The app never works out a server's type by probing it with a saved key and never falls back to another type. Restoring or switching saved archives discards any pending reconfiguration target and unsaved key, so a failed retry cannot retarget a later edit. **Several archives.** Connecting from setup saves through `ConnectionStore.add`: a readable profile with the same server type and address is re-keyed in place (staged, keeping its label), otherwise a new profile is added and becomes active; other profiles are never changed. A changed server type is a different archive and never reuses a key. The current archive's label, type and host are shown above the account on the Mail and Search tabs; tapping it opens the **Archives** picker (each saved archive's label, type and host, plus **Add archive**, which opens setup with Cancel). `ArchiveSession.switchArchive` is disabled during another switch, an account switch or a non-mail request. It first closes the old backend, invalidates its requests and clears account, mail, folders, search, filters and paging, then shows an **Opening <label>…** screen with the destination's type and host. It reads only that profile's saved key and account (`ConnectionStore.connection`), connects with the saved type, and saves through `write(profileId:)`, which makes it active only after it answers. Each archive reopens its own remembered account. A failed switch returns to setup with "Could not open <label> (<type>). …", **Retry saved connection** for that destination and the saved-archives list; the previously active archive stays active for the next start and every profile is kept. Setup lists the saved archives whenever no archive is open and there is more than one, or none is active (for example after Disconnect and forget), and opens nothing automatically. The message reader is a separate route, so attachment transfers and save dialogs are finished or cancelled before the picker can be reached. The demo never appears in, or changes, the saved list. While a saved archive opens at startup (**Connecting to your archive…**) or from the picker (**Opening <label>…**), **Cancel** (`ArchiveSession.cancelOpening`) stops the attempt at once. A cancelled switch reopens the archive that was open before it, if it is still saved; a Cancel while that archive reopens, a cancelled startup restore, or a switch begun with nothing open returns to setup with the saved archives and Retry, so Cancel never loops. Either way, Cancel closes the attempt's client, and connection tokens make the abandoned attempt's late success or failure change nothing, save nothing and activate nothing. Cancel is disabled once secure persistence begins, so an in-flight commit cannot be reported as cancelled. Late restore overviews cannot overwrite newer session state, and disposing the session closes a pending client. The account list has Cancel while it loads; closing it keeps the current account. Connecting to the server (address lookup and connection) is limited to 10 seconds (`archiveConnectTimeout`), because with a VPN such as Tailscale still up while offline, attempts fail only at that limit; the request and response limits after connecting are unchanged. If the server refuses an archive's saved key (401 or 403) when it is restored or switched to, setup also offers **Enter a new key for <label>**, which opens the same change form for that archive only; Cancel returns to setup without opening anything. The interaction acceptance tests in [multi_archive_acceptance_test.dart](../test/multi_archive_acceptance_test.dart) cover the plan's list on synthetic servers. Device, native secure-storage, screen-reader and signed-upgrade checks are still separate. **Settings → Archives** ([archives_page.dart](../lib/screens/archives_page.dart)) lists every saved archive with its type and host, marks the open one, and offers **Rename**, **Change address or key**, **Forget on this device** and **Add archive** (the demo shows Connection settings instead). Rename changes only the label (`ConnectionStore.rename`: control characters become spaces, an empty name returns to the host, at most 60 characters without splitting a character). **Change address or key** opens setup for that archive (`ArchiveSession.openReconfigure`) with the saved address, an empty key and the server type fixed; the saved key is never sent, so a new key must be entered for any change, and a different server type is added as a new archive. A change that would give two archives the same type and address is refused before any request. The new address and key are validated like a new connection, then staged over that profile through `write(profileId:)` (label kept, old key removed after commit) and that archive opens; failure or Cancel keeps the saved archive and the open one. **Forget on this device** asks for confirmation, then removes that profile and its key only (`ConnectionStore.forget`); forgetting the open archive closes it and returns to setup without opening another. Neither contacts the server, changes server mail or revokes the key. **Disconnect and forget connection** in Settings forgets the open archive. Setup asks for the server type explicitly (a Mail-Archiver / Open Archiver choice, Mail-Archiver by default). The choice applies only to a connection made from setup and becomes the active type once that connection succeeds and is saved; cancelling setup or a failed attempt leaves the active connection and its type unchanged. Restoring always uses the saved type, and each type is connected only with its own client (`createArchiveBackend`). Opening or cancelling setup clears the unsaved key, and changing the server type clears it again so the key must be entered for that type; a saved key is never sent with a different type. Startup waits for restoration rather than briefly exposing setup; failures allow retrying saved settings. Disconnect and forget removes those settings and invalidates outstanding requests. It does not delete server mail/user-saved files or revoke the server key.

## Features and rolling design

| Feature | Behavior |
| --- | --- |
| Mail list | Sender initial/avatar, sender, subject, sent date including year (with unavailable-date fallback), attachment indication; folder and paging. |
| Search | Server query, progress/elapsed feedback, one-action clear. Mail tab clears active search. New requests supersede old results; failures show a visible notification with Retry. |
| Folders | Returned hierarchy/counts and All archived mail; selection only. Old responses are ignored after disconnect/replacement. No folder creation/editing. |
| Filters | Inclusive sent-date range with pickers; all/incoming/outgoing; sent/received date, subject, sender or recipient sorting; ascending/descending; reset/apply. Controls grow with large text. Attachment filtering is not implemented. |
| Pagination | Page size 25; Newer/Older, page count and Go to page. Successful navigation scrolls to the first result; failures retain position. |
| Reader | Subject, sender, full sent date/time, bounded prepared body, long-message scrolling, back navigation. Explicit zones use device time; zone-less dates are labelled time zone unspecified. |
| Safe message display | Remote/active content stripped; supported formatting retained. Complex tables flatten or fall back to text. Link confirmation. Simplified display is not a sender trust verdict. |
| Attachments | Confirm save, sanitize filename, private temporary download, destination picker, separate Open confirmation; risky-type caution. |
| Settings | Selected account/server, sync/enabled status, accessible totals/address list, account selection, connection settings, build information and forget. |
| Demo mode | Built-in fictional archive (3 accounts, 70 messages, 11 small attachments) served in memory with the same search, folder, filter, sort, paging, reader and attachment behavior as a server. Always labelled; never saved; no network. |
| Loading/errors | Section loading, empty states, sanitized errors and retry. Mail/Search failures show a snackbar with Retry plus an inline error. Recovery revalidates the other section: folders loading again retries failed mail, and mail loading again retries failed folders (`retryFailedFoldersAfterRecovery`), so no stale error stays after the server is reachable. |

Unread emphasis, editing/deletion, background sync, offline mail, attachment filtering and server administration are not features.

## Safety and attachment lifecycle

Android remembers the MIME type of an explicitly saved attachment alongside its reader-session URI, so provider metadata changes do not change the viewer chooser on repeat Open. PDF filenames use `application/pdf`; other declared types are normalized, with a generic fallback. Existing-file selections use their own provider type, not the original attachment name. Type metadata is removed when the last reader reference is released. This does not inspect file bytes, scan malware or imply a file is safe; save/open confirmations and URI grants are unchanged.

Mail is untrusted. Body preparation has bounded processing, worker-isolate work and safe fallbacks. Remote images/fonts/scripts/styles are not automatically fetched. Link confirmation is not phishing detection. Spam/Junk context and risky extensions prompt caution; there is no malware scanner.

Attachment downloads enforce a 50 MiB (52,428,800-byte) cap on actual response bytes, a two-minute whole-transfer deadline and a 30-second body idle timeout. Oversized metadata/Content-Length is rejected early; unknown or understated lengths cannot bypass streamed accounting. Cancel download or Back/disposal stops only that transfer, closes its client/output and removes partial private data. The archive connection and unrelated requests remain usable. Disk writes are serialized with cleanup. After download, the destination picker owns cancellation and the underlying reader is guarded while export is pending. No new dependency, endpoint, TLS exception or mail mutation is introduced.

Attachments download only after confirmation into private temporary storage. The user chooses a destination. Source cleanup is attempted after save/cancel/failure; interruption or cleanup failure can leave cache copies. User-saved files persist independently.

Open is separately confirmed. Handles last only for the current reader session. Android tracks granted document URIs in native memory. On iOS the app retains the picker URL with balanced scoped access, returns an opaque token and releases access on message disposal/replacement. No bookmark, destination token or extra attachment copy is persisted. After leaving the reader, use Files or save again.

Saving/opening successfully does not make a file safe. See [privacy](../PRIVACY.md) and [troubleshooting](troubleshooting/README.md).

### App lock

Optional and off by default (decisions AL01–AL04). [AppLockController](../lib/app_lock/app_lock_controller.dart) owns the state; [AppLockGate](../lib/app_lock/app_lock_gate.dart) wraps the whole navigator through `MaterialApp.builder`.

- **States:** loading, error, off, locked, authenticating, unlocked. Content is shown only when off, or unlocked and not covered. Before the first unlock (or before the setting is known to be off) the navigator isn't built, so no archive is restored or contacted behind a startup lock. Later locks keep the navigator alive but offstage, excluded from focus, semantics and tickers, and Back is consumed, so in-flight requests finish in memory and nothing is refetched on unlock.
- **Setting:** `app_lock` in secure storage, separate from the `connection*` entries: `{version: 1, enabled, relockSeconds ∈ {0, 60, 300}}`. A missing entry means off; a read failure or damaged value is the error state (covered, with Try again or "Unlock and keep app lock on"), never off. Enabling, disabling and timing changes need a successful prompt first and apply only after the write succeeds.
- **Prompts:** `local_auth` 3.x with device-credential fallback and `persistAcrossBackgrounding: false`. Only the result of the current generation can change state; disposal, a newer prompt or a settings change makes older results stale. Cancel and failure never retry automatically; a prompt starts automatically only on startup, after a relock, or on returning to a locked app.
- **Timing:** time away starts at `hidden`/`paused` while unlocked and is measured on a monotonic clock that includes sleep (Android `SystemClock.elapsedRealtime`, iOS `CLOCK_MONOTONIC`) through the `mailburrow/app_lock` channel. An unknown or backwards clock counts as expired. `inactive` alone only covers. A successful prompt delivered while the app is foreground is accepted. A success delivered while the app is away (the Android PIN/pattern screen and iOS Face ID do this just before resume) is held and accepted only if the app returns within `promptReturnWindow` (3 s) on the monotonic clock; a later return is a genuine leave and stays locked. The prompt itself may settle its lifecycle events, but a later leave during a settings/repair write is preserved and checked before content is revealed. Time in the system save screen counts. A download that completes while covered does not open a new native save picker: its temporary file is cleaned and the user saves again after unlocking. Already-open native pickers retain their normal cancellation behavior. The lock/recovery surface scrolls at large text sizes.
- **Prompt-return race:** after a background success resumes, the monotonic acceptance check also verifies that the app is still foreground and no newer leave occurred while the clock result was pending. A second leave invalidates that acceptance; it cannot authorize a later return.
- **App switcher:** Android 13+ uses `setRecentsScreenshotEnabled(false)` while app lock is on, reapplied on resume; `FLAG_SECURE` is never used, so screenshots stay allowed. Older Android relies on the Flutter cover shown on `inactive` (best effort). iOS adds a native cover on `UIScene.willDeactivateNotification`.
- **Limits:** a UI access control, not encryption. It doesn't protect saved files, the clipboard, screenshots, rooted or jailbroken devices, or someone who knows the device credential. Reinstalling isn't a guaranteed reset (iOS Keychain can survive uninstall).

## Architecture and source map

```text
Flutter UI → ArchiveBackend (implemented by ArchiveApi) → configured HTTPS Mail-Archiver
     ├→ platform secure storage: connection restoration
     ├→ bounded body preparation → safe reader
     └→ confirmed download → native save/open bridge
```

| Backend interface | [archive_backend.dart](../lib/archive_backend.dart): the `ArchiveBackend` interface, the only way the app reaches a server (accounts, folders, search, message, attachment download, stats, cancel, close). Account, message and attachment method parameters use opaque text IDs. Mail-Archiver validates numeric wire IDs inside its adapter. Results are typed models from [archive_models.dart](../lib/archive_models.dart) (`ArchiveAccount`, `MailPage`/`MailSummary`, `MailMessage` with `MailAttachment`, `ArchiveStats`); each backend converts its own responses and rejects malformed ones with a `FormatException`, so screens and the session never read a server's JSON. Each backend also declares fixed `ArchiveCapabilities` ([archive_capabilities.dart](../lib/archive_capabilities.dart)): folders, date-range and direction filters, accepted sort fields and orders, whether match totals are estimates, and whether per-key archive totals exist. Capability sort sets are immutable snapshots; declarations require known sort options and the default sent-date/descending sort. `allows()` rejects invalid direction/date-range input as well as unsupported features. Capabilities are never detected by probing a server. Mail-Archiver and the demo report every capability. The session and screens follow them: without `folders` no folder request is made and the folder picker, reload button and folder errors are hidden; the filter sheet offers only supported date, direction and sort choices (a sort choice with one option is hidden, and the Filters action is hidden when nothing is adjustable), and applied filters are reduced to supported values before any request; with `estimatedTotals` the result line says "about N matches"; without `archiveStats` Settings never calls `stats()` and hides the totals block while still listing accounts. While disconnected the session reports full capabilities. `DemoArchive.load`/`parse` accept narrowed capabilities for tests, and a narrowed demo throws if asked for anything it does not support. Implementations:
- `ArchiveApi` for Mail-Archiver. It also owns the shared HTTPS transport (pooled client, no redirects, size and time limits, per-call cancellation), with `authorize` and `isMailRequest` hooks.
- `DemoArchive`, which serves the built-in demo data without any network access (see Demo mode).
- `OpenArchiverApi` ([open_archiver_api.dart](../lib/open_archiver_api.dart)), in progress on the Open Archiver branch and selectable in setup there; it is not released. It targets v0.6.2, sends `X-API-KEY`, maps ingestion sources to accounts labelled by source name (`ArchiveAccount.name`), and lists a source through its browse route, with exact totals. Searches, date filters and oldest-first order go through `/search` limited to that source, with estimated totals marked by `MailPage.totalIsEstimate`. Only the list fields are read from search hits; their body and attachment text is dropped with the response. IDs are validated before any URL is built. Preserve-original classification requires an explicit boolean; a missing or malformed flag is rejected rather than assumed safe. Search timestamps accept negative Unix epochs, with out-of-range values rejected as format errors. Folders and archive totals are refused.
  - **Opening messages** follows the approved phone budgets:
    - A message opens only when this backend listed it and the source's `preserveOriginalFile` is explicitly false. The policy is read from the sources list, refreshed once if unknown. Sources that keep full originals carry attachments inside `raw`, so they are refused before any request, with a reason shown in the reader.
    - The detail response is read as it streams by `OpenArchiverDetailReader` ([open_archiver_detail.dart](../lib/open_archiver_detail.dart)), which turns `raw.data` straight into bytes and builds only the other fields. It enforces a 40 MiB wire cap (up front from `Content-Length` and while streaming), a 10 MiB decoded-message cap, a 4 MiB cap on other JSON, and a 60 s read time. Duplicate JSON keys and malformed raw-byte numbers are rejected; metadata is additionally limited to 64 nesting levels and 100,000 values to bound allocation overhead. MIME delimiters must occupy a complete delimiter line so body text sharing a boundary prefix is preserved.
    - `readMimeBodies` ([mime_bodies.dart](../lib/mime_bodies.dart)) then runs in a background isolate with a 5 s timeout. It decodes only the first text and HTML bodies, counts inline parts and skips attachments. It checks depth 32, 500 parts, 256 KiB of headers and the decoded total before the work each limit bounds, and records problems instead of throwing. It handles UTF-8, US-ASCII, ISO-8859-1 and Windows-1252.
    - Subject, sender, date and folder path come from the response's metadata. Attachment records keep their storage paths for saving.
  - **Saving attachments** works only for an attachment listed by a message this backend opened, and only from that message. It goes through `GET /storage/download?path=<storagePath>` on the shared download path (`ArchiveApi.downloadTo`), which has its own client, the 50 MiB limit, deadline and idle timeouts, and deletes the partial file on failure. That route streams without a `Content-Length`, so the record's `sizeBytes` is enforced instead: above the limit the save is refused before any request, and the bytes must match it exactly. Download URLs must use the configured HTTPS origin, without user information or fragments. Attachment handles are registered only after the complete message validates, and reopening replaces that message’s previous handles. Storage paths are validated when the message opens (non-empty, at most 1024 characters, no control characters). |

## API contract currently consumed

These are existing implemented calls, not a complete upstream capability catalog. Verify new fields/endpoints against reliable sources or established context. Prefix with the configured server base path. All operations below are GET/read-only; no mail mutations.

| Route below `/api/v1/` | Use and known shape |
| --- | --- |
| `accounts` | Account-object list; established fields include id, emailAddress, lastSync and isEnabled. Selected account matched by id; only returned entries displayed. |
| `stats` | Object with emails/accounts/attachments counts. UI labels totals across accessible accounts, not selected-account totals. Invalid counts fail visibly. |
| `accounts/{id}/folders` | Returned tree flattened for display; do not invent Inbox or treat selection as creation. |
| `emails` | accountId, q, page, pageSize=25, optional folder and filter parameters. Response: items, page, totalPages, optional totalItems. |
| `emails/{id}` | Used fields include subject, from, sentDate, textBody/htmlBody, folderName, attachments. List entries use from, subject, sentDate and hasAttachments. |
| `emails/{emailId}/attachments/{attachmentId}` | Explicitly requested file streamed to a private temporary destination. |

No guessed received-date fallback is used. Attachment indication uses hasAttachments; details use returned attachments. Showing dates/accounts needs no additional detail/attachment fetch.

Local JSON limit: 8 MiB received bytes before decoding, including streamed/declared-size checks, with decoding off the UI isolate. Downloads stream separately. Request generations prevent late results replacing newer searches or forgotten connections. Backend availability/compatibility remain external dependencies.

Reader loads have per-reader cancellation (`MessageLoad` and `CancellableMessageBackend`): Back cancels as soon as the route pops, before its transition finishes, and disposal is a fallback. Shared HTTP requests made by that load are stopped without closing the archive or cancelling another reader, even with an equal message ID. Late Open Archiver results cannot start MIME/body preparation or register attachment handles after cancellation. Already-running bounded preparation may finish, but its result is discarded.

## Failure and recovery decisions

Preserve useful messages and scroll position on failed refresh. Show Mail/Search errors visibly with Retry, retain the inline error, and preserve current page/query/filter context. Never echo response bodies, keys or private hosts.

Folders/information retain their own loading/errors. A successful section retries a prior failed mail load instead of assuming endpoint permissions are equivalent. Continued denial/timeout becomes the current error. A section success must not dismiss unrelated setup/storage failures.

The setup guide and website describe Open Archiver 0.6.2 source-scoped read/search roles, source IDs from the View emails URL, and its shared per-client-IP rate budget. Public copy distinguishes the linked RC9 binary from 0.4.0 source features. Privacy notices cover connection validation as well as active browsing, full message/attachment text in search responses, server audit logging, response budgets and retryable secure-storage cleanup.

Update affected behavior and decisions with future changes. See [maintenance rules](development/documentation.md).

Synthetic phone-memory fixtures must retain their intended MIME structure after import. Legacy-charset alternatives are selected bodies, CID images are explicitly inline, and the many-parts fixture uses body parts. The RSS sampler parses field names independent of proc ordering and does not use cross-UID signal permission as a process-liveness test; sampled peaks and process-lifetime VmHWM have different limits, and before/after snapshots do not establish peak memory. See [lab stress checks](development/test-archive-servers.md#phone-memory-check-with-stress-mail).

The [stress-fixture checker](../tools/oa_stress_check.py) validates selected MIME bodies and app structural limits before lab fixtures count as retained. Diagnostics use fixed MIME-name allowlists; unknown server-supplied names are never echoed. Malformed or truncated listings, duplicate cases and invalid raw buffers fail verification, and its network reads have a bounded diagnostic budget. This is structural validation, not byte identity or device-memory evidence.

The Open Archiver lab checker distinguishes revoked-key refusal from the separately supplied expired-key fixture. It rejects reusing an admin, reader or revoked key for expiry testing before making requests. HTTP 401 alone does not establish why a key was rejected; expiry status needs independently verified fixture provenance. A missing genuine expired fixture stays skipped/untested.

The [Bichon lab checker](../tools/bichon_lab_check.py) is a standalone diagnostic tool; the Bichon adapter and setup integration are implemented on the development branch but are not yet released. It uses GET plus allowlisted read-only search POST, validates restricted-account reads against synthetic fixtures, and reports bounded, sanitized summaries. Mutation-denial probes remain a separate disposable-lab procedure; a checker pass is not a completed feasibility or device gate.

The separate [Bichon write-denial procedure](../tools/bichon_write_denial.py) mutates only a positively identified sacrificial lab message, validates both tokens can read it, and uses admin controls before interpreting reader 403 responses. It verifies envelope state and deletion cleanup without reporting message values. Host tests are synthetic; this is not app functionality or live authorization evidence.

Known Bichon folder states `fetching` and `error` produce retry guidance rather than an unsupported-version diagnosis. A contract failure identifies an unreadable response and the tested adapter version; it does not establish which server version is actually running.

The [Bichon measurement-fixture generator](../tools/bichon_fixtures.py) writes a bounded deterministic fictional mbox with large bodies, a 45 MiB attachment and a full search page. It refuses existing files and removes newly created partial output on failure. Verify actual imported response sizes and fixture readiness separately; generation tests do not establish a phone or release-artifact pass.

The lab-only `tools/bichon_fixture_cleanup.py` defaults to a dry run, validates exact generated fixture identities, one disposable folder and the unchanged baseline, then permits deletion only with its explicit flag. It never deletes folders. Complete bounded search inventories must have stable totals and unique scoped IDs. Keep the fictional lab quiescent; preflight checks cannot make the later deletion atomic.
